========================================
Sprint 2 - Digital Asset Authentication
========================================

Assets

POST /api/assets/upload
- Upload an image.
- Automatically:
  - Store file
  - Generate SHA-256
  - Generate pHash
  - Extract metadata
  - Save asset
- Status: implemented

POST /api/assets/check
- Temporarily process a JPG, PNG, or WebP image without registering it.
- Requires JWT authentication.
- Checks exact SHA-256 matches first, then finds the closest stored perceptual hash using bit-level Hamming distance.
- Perceptual responses include similarity classification, distance, applicable threshold, and hash bit length.
- Deletes the temporary upload after processing.
- Returns full asset identity only for the authenticated owner; cross-owner matches use pseudonymous owner and asset references.
- Status: implemented

GET /api/assets
- List authenticated user's assets.
- Owner-scoped and newest-first.
- Status: implemented

GET /api/assets/:id
- Return asset details.
- Enforces authenticated ownership.
- Status: implemented

GET /api/assets/:id/content
- Return the stored image for an owned asset.
- Requires JWT authentication and enforces ownership.
- Status: implemented

DELETE /api/assets/:id
- Delete asset.
- Status: planned

GET /api/assets/:id/hash
- Return SHA-256 and pHash.
- Enforces authenticated ownership.
- Status: implemented

GET /api/assets/:id/metadata
- Return extracted metadata.
- Enforces authenticated ownership.
- Status: implemented

Verification

POST /api/verifications
- Compare a temporary image against one selected asset owned by the authenticated user.
- Requires JWT authentication and multipart fields `assetId` and `file`.
- Produces exact, strong visual, possible visual, or no meaningful match evidence.
- Saves thresholds, pHash distance, safe metadata differences, and report timestamps without storing the comparison image.
- Status: implemented

GET /api/verifications
- Return only the authenticated user's verification history, newest first.
- Status: implemented

GET /api/verifications/:reference
- Return one owner-scoped report by its pseudonymous VR reference.
- Status: implemented

Vaults

POST /api/vaults
- Create a private organizational collection with a safe `VT-XXXXXX` reference.
- Requires a Vault password; only its bcrypt hash is stored.
- Requires JWT authentication.
- Status: implemented

GET /api/vaults
- List only the authenticated user's Vaults, newest first, with real collection statistics and preview assets.
- Status: implemented

GET /api/vaults/:reference
- Return one owner-scoped Vault. Asset memberships are omitted while it is locked.
- Status: implemented

POST /api/vaults/:reference/unlock
- Verify the Vault password and create a temporary server-side grant for the current JWT session.
- Unlock duration uses the Vault's 5, 10, or 30 minute setting and defaults to 10 minutes; `VAULT_UNLOCK_TTL_SECONDS` can provide a server override.
- Status: implemented

POST /api/vaults/:reference/lock
- Revoke the current JWT session's grant for this Vault immediately.
- Status: implemented

POST /api/vaults/:reference/change-password
- Require `currentPassword`, `newPassword`, and `confirmPassword`.
- Optionally accept `autoLockMinutes` as 5, 10, or 30.
- Replace the bcrypt hash and revoke every active unlock grant for the Vault.
- Repeated incorrect current-password attempts use the same Vault rate limit as unlock.
- Status: implemented

POST /api/vaults/:reference/reset-password
- Account-recovery flow requiring `accountPassword`, `newPassword`, and `confirmPassword`.
- This is authenticated application recovery, not cryptographic recovery.
- Incorrect account-password attempts use the same per-user, per-Vault rate limit.
- Replace the bcrypt hash and revoke every active unlock grant for the Vault.
- Status: implemented

PATCH /api/vaults/:reference
- Update an owned Vault's name or description.
- Status: implemented

DELETE /api/vaults/:reference
- Delete only the Vault and its memberships; registered assets and their stored data remain.
- Status: implemented

POST /api/vaults/:reference/assets
- Add one or more assets already owned by the authenticated user; no file is copied or reprocessed.
- Body: `{ "assetIds": [1, 2] }`
- Rejects duplicate memberships and assets owned by another user.
- Status: implemented

Protected asset rule
- If an asset belongs to multiple password-protected Vaults, every protecting Vault must be unlocked for the current JWT before content, hashes, metadata, or a new Verification comparison is allowed.
- Ownership Check may compare stored fingerprints internally but does not return protected content or private metadata.
- Password protection controls access; asset files are not encrypted at rest.
- Unlock attempts are limited per authenticated user and owned Vault. Defaults are 5 attempts per 15-minute window followed by a 15-minute block; configure with `VAULT_UNLOCK_MAX_ATTEMPTS`, `VAULT_UNLOCK_WINDOW_SECONDS`, and `VAULT_UNLOCK_BLOCK_SECONDS`.

DELETE /api/vaults/:reference/assets/:assetId
- Remove only the asset-to-Vault relationship.
- Status: implemented

Sprint Summary
========================================

Sprint 1: Authentication, JWT, Protected Routes, Dashboard Summary
Sprint 2: Image Upload, SHA-256, pHash, Metadata Extraction, Duplicate Detection, Verification Reports
Sprint 3: Organizational Vault collections implemented; OCR and document verification remain planned
Sprint 4: Blockchain Ledger, Ownership Transfer, Marketplace, Fractional Ownership, Wallet Integration, Final UI Polish

Notes

- Authentication, health, dashboard summary, upload, asset listing/detail/content/hash/metadata, temporary ownership checking, verification reports, and private organizational Vaults are implemented.
- The remaining endpoints are roadmap items and should be added as the project grows.
- This file is intended as the canonical API checklist for current and future work.
